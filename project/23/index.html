Hotspot

## 痛点：为什么需要另一个热点工具？ 每天刷 RSS、翻科技媒体、搜搜索引擎，才能知道技术圈发生了什么。但这个过程充满噪声： - **RSS** 只管推文章，不管质量，订阅源一多就是信息洪流 - **搜索引擎** 前几页全是 SEO 软文和广告 - **时间线** 按热度排序，最新发布的内容永远排在后头 市面上的 AI 搜索工具呢？要么付费，要么不支持联网搜索。即使支持联网，也得自己写爬虫去抓取、清洗、去重——这本身就是一个项目的工作量。 **能不能让 AI 替我完成这条流水线？** 输入关键词，自动联网搜索、去广告、按时间排序、整理多角度观点、最后出一份干净的报告。 于是有了 **Hotspot**。 --- ## 项目定位 Hotspot 是一个基于 **DeepSeek 免费网页版** 的自动化技术热点搜索工具。 - **纯免费** —— 不需要 API Key，不需要付费订阅 - **比 RSS 智能** —— AI 理解什么是技术热点，而不是机械地推送关键词匹配 - **比搜索干净** —— 自动去广告、去重、验证链接可用性 - **自动化产出** —— 一键运行，生成结构化 JSON + 可视化 HTML 报告 ## 和 TrendRadar 有什么不同？ TrendRadar（58.6K+ Star）是市面上最知名的一站式热点聚合工具之一。我在做 Hotspot 之前仔细研究过它，结论是：**数据源决定了天花板。** TrendRadar 从微博、知乎、B 站、抖音等 **11+ 社交平台** 的热榜和 RSS 源抓取内容。这些平台的热榜天然偏向社会热点、娱乐八卦。即使它提供了强大的关键词语法过滤（`+` 必须词、`!` 排除词、正则匹配）和 AI 兴趣筛选，也只是在社交热榜的结果之上做过滤——**源数据就不是技术内容，过滤得再好也得不到纯技术热点。** 结果就是：搜到的所谓"技术热点"大多是 **融资新闻、市场分析、大佬言论** 这类风口话题。真正的技术进展——Rust 1.96.1 发布了什么、Docker Engine 29.6.0 有哪些变更——在微博热榜和 B 站热门上是看不到的。 Hotspot 的解决思路是：**绕过社交平台热榜，让 AI 直接理解什么是技术热点。** DeepSeek 的联网搜索能力让它能直接访问全网技术内容，而不是在二手数据上做加工。 --- ## 技术架构 项目结构非常精简，核心代码只有三个文件： ``` hotspot/ ├── cli.py # 入口编排：日志、启动、循环、汇总 ├── deepseek.py # 浏览器自动化基座（Playwright + 反检测） ├── hotspotter.py # 搜索逻辑：提示词、解析、验证、报告 ├── config.json # 配置（关键词、账号、提示词模板） └── template.html # HTML 报告模板（深色主题、毛玻璃卡片） ``` 依赖同样精简，五个库搞定： | 组件 | 用途 | |------|------| | `playwright` | Chromium 浏览器自动化 | | `httpx` | URL 可用性验证（HEAD + GET 降级） | | `beautifulsoup4` + `lxml` | HTML 解析，提取引用链接 | | `demjson3` | JSON 宽松解析兜底 | ### 浏览器自动化与反检测 DeepSeek 网页版会对自动化工具进行检测，直接使用 Playwright 会被拦截。解决方案是**双重反检测**： ```python # 1. 启动参数隐藏自动化特征 browser = playwright.chromium.launch( args=["--disable-blink-features=AutomationControlled"] ) # 2. 页面级别注入反检测脚本 page.add_init_script(""" Object.defineProperty(navigator, 'webdriver', { get: () => undefined }); Object.defineProperty(navigator, 'plugins', { get: () => [ { name: 'Chrome PDF Plugin', filename: 'internal-pdf-viewer' }, { name: 'Chrome PDF Viewer', filename: 'mhjfbmdgcfjbbpaeojofohoefgiehjai' }, { name: 'Native Client', filename: 'pnacl' }, ], }); window.chrome = window.chrome || {}; window.chrome.runtime = {}; """) ``` 两个措施缺一不可。不注入脚本的话，`navigator.webdriver` 为 `true` 会直接暴露自动化身份。 ### 流式回复的稳定检测 DeepSeek 采用流式生成，文本逐字出现在 DOM 中。不能等固定时间（太短截断、太长浪费时间），也不能单次检测（流式写入可能短暂停顿）。 核心算法：**每 500ms 轮询一次回复框的文本长度，连续 3 次（1.5 秒）长度不再变化才认为生成完毕。** ```python while time.time() - start < timeout: if reply.count() > 0: text = reply.last.text_content() or "" current_len = len(text.strip()) if current_len > 3: if current_len == last_len: stable_polls += 1 else: stable_polls = 0 if stable_polls >= 3: return self._get_reply_with_links() last_len = current_len self._page.wait_for_timeout(500) ``` 实测在 **20-60 秒** 内完成检测，比固定等待快 2-5 倍。 --- ## 搜索管线 每个关键词的完整搜索流程如下： ``` 构建提示词 → 发送给 DeepSeek → JSON 解析 → 引用链接填补无效 URL → URL 去重 → HEAD 请求验证链接可用性 → 过滤不可达链接 → 保存结果 ``` ### 提示词模板 提示词是项目的核心竞争力。同样的需求不同的措辞，DeepSeek 的输出质量天差地别。当前模板的关键约束： - **必须开启联网搜索** —— 要求 DeepSeek 搜索近 7 天（尤其 24-48 小时）的全网内容 - **结构化输出** —— 严格的 JSON 格式，字段包含 `title`、`summary`、`source`、`url`、`published_time`、`perspectives`（多角度观点） - **URL 真实性铁律** —— 宁可 `null` 不要假链接，禁止根据来源名称拼接 URL - **中文引号替代** —— 要求使用「」代替 ASCII 双引号，避免 JSON 解析失败 ### JSON 解析兜底 DeepSeek 的输出经常混入 ASCII 双引号作为中文引号，导致 `json.loads` 失败。解析策略分两层： 1. 去掉 Markdown 代码块包裹后调用标准 `json.loads` 2. 失败则用 `demjson3` 做宽松模式解析（容忍非标准引号、多余逗号） 两层都不通过才判定为失败。这套策略将 JSON 解析成功率从 **约 60% 提升到 95% 以上**。 ### URL 验证 AI 编造链接是最大的坑。DeepSeek 会生成 `ithome.com/0/000/000.htm` 这种看似合理实则不存在的链接。 三重防护： 1. **提示词约束** —— 明确要求 "宁可 null 不要假链接" 2. **引用链接匹配** —— 回复中的 `-8`、`--5` 标记对应底部的真实引用链接，自动匹配填补 3. **HEAD 请求验证** —— 对每个 URL 发 HEAD 请求（超时 8 秒降级为 GET），404/超时/连接失败直接剔除 ### Session 持久化 首次登录时填写账号密码，登录成功后将 Cookie 保存到本地文件。后续运行自动加载，无需重复登录。 关键设计：**登录成功后立即保存 Session**。即使账号后续被封禁（自动化操作触发了风控），也能跳过登录直接进入，因为封禁检测会识别到违规提示并生成空报告，不会卡死。 --- ## 输出 运行 `uv run python -m hotspot` 后： ``` results/{日期}/{时间}/ ├── run.log # 完整运行日志 ├── report.json # 聚合报告（JSON，程序可读） ├── report.html # 可视化报告（HTML，浏览器直接打开） ├── {关键词1}.json # 每个关键词的详细结果 └── {关键词2}.json ``` ### HTML 报告 深色主题，毛玻璃卡片风格，支持 Tab 切换关键词。每条热点包含： - 标题 + 来源 + 发布时间 - 核心摘要（约 50 字） - 可点击链接（已经过可用性验证） - 多角度观点（不同立场 / 争议观点） - 舆情趋势总结 单文件、零外部依赖，浏览器直接打开即可。 --- ## 部署方案 ### 本地一键部署 `deploy.bat` 脚本完成全流程： ``` 清理旧数据 → 运行搜索 → 检查是否有热点数据 → 推送到 gh-pages 分支 ``` 使用 `git worktree` 避免切换分支导致工作区混乱。无热点数据时自动跳过部署，确保线上页面不会因为一次失败运行变成空白页。 ### GitHub Actions 配置了每天 08:00 / 20:00 定时触发。但存在一个实际问题：GitHub Actions 的 Ubuntu 服务器在美国，访问 DeepSeek 会被 Cloudflare 拦截。 实际推荐方案是**本地运行 + 推送到 gh-pages**。我个人的工作流是：每天在本地跑一次 `deploy.bat`，结果自动推送到示例站点 [hotspot.lxpavilion.top](https://hotspot.lxpavilion.top)。 --- ## 开发历程踩坑记录 整个项目大概花了一周，方向经历了三次大转折： ### 1. DuckDuckGo 搜索 — ❌ 最开始用 DuckDuckGo 的搜索 API，不需要注册，免费调用。但国内网络连 DuckDuckGo 极慢，一个请求要 **40-60 秒**，完全没法用。 ### 2. Bing 爬虫 — ⚠️ 换成直接爬 Bing 网页搜索，速度快了很多（约 2 秒），还能解析摘要里的时间信息做筛选。但搜到的内容混杂，广告和无关页面多，需要大量过滤逻辑。**花了大量时间写过滤规则，本质是在和垃圾内容作斗争。** ### 3. DeepSeek 网页版 — ✅ 试了一下 DeepSeek 的联网搜索后，效果惊艳——能直接返回结构化的热点信息，自带多角度观点提取和舆情总结。**方向彻底变了：不再爬搜索引擎，而是让 AI 直接理解什么是技术热点。** ### 后续的坑 - **URL 编造** —— DeepSeek 会编造链接，最终用提示词约束 + HEAD 验证 + 引用匹配三重防护解决 - **账号封禁** —— 自动化触发风控被禁言，加上封禁检测后流程能完整走完 - **Session 管理** —— 从手动登录到自动登录到 Session 持久化，折腾了很久 - **对话清理** —— 不删对话导致每搜一个关键词就多一个历史记录，浏览器内存爆炸 --- ## 总结：这个项目最有价值的不是代码 写 Hotspot 的过程中最大的收获： 1. **AI 的输出不能直接信任。** 链接要验证、JSON 要兜底、回复要等稳定——每一层都是血的教训 2. **提示词是核心竞争力。** 同样的需求、不同的措辞，AI 的输出质量天差地别。写好提示词比写好代码更重要 3. **自动化要考虑所有异常路径。** 封禁、拦截、超时、JSON 解析失败——每一条都实际遇到过 4. **不要为了自动化而自动化。** 本地运行 + 推送往往比 CI 更可靠。GitHub Actions 被 Cloudflare 拦住的教训至今仍然适用 --- > **项目地址**：[github.com/PC2005-cloud/hotspot](https://github.com/PC2005-cloud/hotspot) > **示例站点**：[hotspot.lxpavilion.top](https://hotspot.lxpavilion.top) > > 欢迎 Star、提 Issue，或者 fork 一份自己跑着玩。
