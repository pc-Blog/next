SmartMall

从零到一，构建一个生产级微服务电商平台。

项目简介

SmartMall 是一个完整的 B2C 单商户电商平台，采用当下主流的 Spring Cloud Alibaba 微服务架构，涵盖前台商城系统与后台管理系统两大模块，实现了从商品管理、用户登录、购物车、订单下单到支付回调、秒杀抢购的完整电商业务闭环。

项目不仅是一个 CRUD 集合，更着重解决了分布式场景下的服务治理、分布式事务、高并发库存扣减、购物车合并、幂等性设计等真实生产环境中的核心技术难题。

公共模块（common）

为保证代码复用与风格统一，所有服务共享一个 common 模块，封装了：

  • 统一响应体 R：标准化的 JSON 返回格式
  • 全局异常处理：BaseException + BaseCodeEnum 错误码体系
  • MyBatis-Plus 配置：分页插件、乐观锁
  • Feign 配置：请求拦截器（透传 Session）、Sentinel 整合
  • RabbitMQ 配置：手动确认、发布确认、退货回调
  • Redis 配置：Spring Session Redis + 分布式会话（GULISESSION Cookie，父域 gulimall.com）
  • 校验分组：JSR-303 分组校验（AddGroup / UpdateGroup）
  • ThreadPool 配置：统一异步线程池

网关路由设计

网关是整个系统的流量入口，采用了路径路由 + 域名路由的双重策略：

  • 后台管理 API：/api/product/** → lb://product，/api/order/** → lb://order，以此类推
  • 前台商城页面：通过二级域名区分业务模块 —— search.gulimall.com → 搜索页，item.gulimall.com → 商品详情页，auth.gulimall.com → 登录注册页，cart.gulimall.com → 购物车页，order.gulimall.com → 订单页，seckill.gulimall.com → 秒杀页

所有请求统一经过 Gateway，由 Nacos 做服务发现，Sentinel 做流量防护。

核心业务设计与技术亮点

1. 商品系统 —— 三级分类 & ES 全文检索

三级分类树：分类采用 parent_cid 自关联设计，通过一次全量查询 + 内存递归组装成树形结构，并按 sort 字段排序。热门分类数据使用 Spring Cache（sync = true）缓存至 Redis，防止缓存击穿。

SPU/SKU 模型：遵循电商标准建模 —— SPU（标准化产品单元）描述通用属性（品牌、描述、图片集），SKU（库存量单位）承载具体销售属性（颜色、内存、价格）。商品上架时，系统将 SPU 基本信息 + 所有 SKU 数据汇总写入 Elasticsearch，同步推送至搜索服务。

商品详情页：使用 CompletableFuture 异步编排，并行加载 SKU 信息、销售属性、SPU 描述、规格参数、SKU 图片、秒杀信息等 6 个数据模块，最终 allOf() 统一返回，显著缩短页面响应时间。

2. 搜索系统 —— Elasticsearch 聚合筛选

搜索服务基于 Elasticsearch 构建，支持：

  • 条件组合查询：Bool Query 组合关键字、分类、品牌、属性、价格区间、库存状态，支持多字段排序与分页

3. 购物车系统 —— 离线购物车 & 登录合并

购物车数据完全存储在 Redis（Hash 结构），使用 user-key 作为临时用户标识：

  • 未登录用户：通过浏览器 Cookie 存储 user-key（UUID，30 天有效期），购物车数据存储在 gulimall:cart:{user-key} 中
  • 已登录用户：购物车数据存储在 gulimall:cart:{userId} 中
  • 购物车合并：用户登录后，系统自动将临时购物车中的商品逐项合并到用户购物车，新商品新增，已有商品数量累加，合并完成后清除临时数据

4. 订单系统 —— 分布式事务 & 最终一致性

下单流程是项目中最复杂的业务流程，涉及多个服务的协同调用：

<!-- 预留：下单流程图 -->

（图片：下单流程时序图）

4.1 订单确认

用户进入确认页时，系统并行异步加载四类数据：

  • 收货地址列表（Member 服务）
  • 购物车选中商品（Cart 服务）
  • 商品库存信息（Ware 服务）
  • 用户积分（Member 服务）

同时生成幂等性令牌（UUID），写入 Redis 并设 30 分钟过期，用于后续提交订单的防重复提交。

4.2 订单提交

验证令牌（Lua 脚本原子删除）
  → 创建订单 & 订单项
    → 验证价格
      → 锁定库存（远程调用 Ware 服务）
        → 发送延迟消息到 RabbitMQ（超时关单）
          → 清除购物车

关键设计：

  • 幂等性：使用 Redis + Lua 脚本保证"验证令牌 + 删除令牌"的原子性，从源头防止重复下单
  • 库存锁定：Ware 服务采用"遍历仓库、就近锁定"策略 —— 对每个 SKU 遍历有库存的仓库列表，执行 SQL update wms_ware_sku set stock_locked = stock_locked + #{num} where sku_id = #{skuId} and ware_id = #{wareId} and stock - stock_locked >= #{num}，扣减成功则停止遍历
  • 最终一致性：库存锁定成功后发送 stock.locked 消息；订单超时后触发库存解锁，通过 RabbitMQ 保证订单与库存状态的最终一致

5. 库存系统 —— RabbitMQ 可靠消息与解锁流程

库存的锁定与释放是分布式事务的典型场景，项目设计了一套基于 RabbitMQ 的可靠消息机制：

用户下单 → 锁定库存 → 发送 stock.locked 消息（延迟队列）
                            ↓
                    订单超时未支付 → 关闭订单 → 发送 order.release.other
                                                      ↓
                                              库存解锁（Ware 服务）

解锁逻辑：Ware 服务收到解锁请求后，查询工作单详情：

  • 若对应订单为 null（订单创建失败）→ 解锁库存
  • 若订单状态为 已取消 → 解锁库存
  • 若订单状态为 已支付 → 不解锁（正常交易完成）

消息采用手动确认模式（basicAck / basicReject），处理失败的消息重新入队，保证消息不丢失。

6. 秒杀系统 —— 高并发架构设计

秒杀是电商中最具挑战性的场景，系统从多个层面做了高并发优化：

6.1 定时上架

通过 @Scheduled 定时任务，每天凌晨扫描未来 3 天的秒杀活动，将场次和商品信息预热到 Redis：

  • 活动场次：seckill:sessions:{start}_{end} → Redis List，存储 sessionId-skuId
  • 商品详情：seckill:skus → Redis Hash，Key 为 sessionId-skuId，Value 为 SeckillSkuRedisTo（含商品信息、秒杀价、随机码、信号量 key）
  • 库存信号量：seckill:stock:{randomCode} → Redisson RSemaphore，初始值为秒杀库存数

6.2 秒杀流程

验证活动时间
  → 验证随机码（防止提前刷接口）
    → Redisson 信号量 tryAcquire()（原子扣减库存）
      → Redis SETNX 幂等占位（防重复下单）
        → 发送 MQ 消息 → 异步创建订单

核心优化点：

  • Redis 预热：商品数据全量缓存，秒杀请求不穿透数据库
  • Redisson 分布式信号量：替代数据库行锁，原子扣减，性能量级提升
  • 随机码机制：为每个秒杀商品生成 UUID 随机码，商品未到秒杀时间时不暴露秒杀接口
  • 异步下单：秒杀成功只扣减信号量 + 发送 MQ 消息，订单创建由 Order 服务异步消费完成，快速响应客户端
  • Sentinel 限流：在查询秒杀商品接口上配置 Sentinel 流控规则，保护下游服务

7. 认证系统 —— 分布式会话 & 社交登录

认证中心统一管理用户身份，支持多种登录方式：

  • 账号密码登录：调用 Member 服务验证，成功后写入 Session
  • 短信验证码登录：60 秒防刷限制，验证码存入 Redis（5 分钟过期），验证后删除（一次性令牌）
  • 社交登录（OAuth2.0）：已集成微博、GitHub 第三方登录回调

分布式会话：基于 Spring Session + Redis 实现，所有服务共享 Session。通过配置 GULISESSION Cookie（domain: gulimall.com，path: /），确保用户在 auth.gulimall.com 登录后，在 cart.gulimall.com、order.gulimall.com 等子域名下均可识别登录状态。

每个需要登录态的服务通过自定义 LoginUserInterceptor，从 Session 中提取用户信息并存入 ThreadLocal，业务代码通过 LoginUserInterceptor.threadLocal.get() 直接获取。

8. 支付系统 —— 支付宝 & 微信支付

集成支付宝沙箱环境与微信支付 BestPay SDK：

  • 支付宝：PC 网站支付（AlipayTemplate），下单 → 生成支付表单 → 同步跳转 + 异步通知

分布式治理

服务发现 & 配置中心 —— Nacos

所有微服务启动时向 Nacos 注册，Gateway 通过服务名（lb://service-name）做负载均衡转发。公共配置（数据源、Redis、RabbitMQ、Sentinel 等）通过 Nacos Config 统一管理，支持动态刷新。

熔断降级 —— Sentinel

在 Feign 调用、秒杀查询等关键链路上配置 Sentinel 流控与降级规则，当下游服务不可用时快速失败，防止级联雪崩。

链路追踪 —— Zipkin

集成 Micrometer Tracing + Zipkin Brave，使用 B3 传播协议，实现跨服务的调用链追踪与性能分析。

分布式事务

项目未引入 Seata 等重型分布式事务框架，而是通过 RabbitMQ 最终一致性 + 本地事务 的组合方案，以更轻量的方式实现跨服务数据一致性：

  • 订单创建 → 库存锁定 → MQ 延迟消息 → 超时回滚
  • 库存锁定 → MQ 消息 → 订单取消 → 库存解锁

项目展望

SmartMall 未来可在以下方向持续演进：

  • 容器化部署：编写 Dockerfile 与 Kubernetes 编排脚本，实现一键部署

  • 灰度发布：结合 Nacos 权重路由 + Gateway 流量染色，实现平滑上线
  • 响应式编程：WebFlux 替代 WebMvc，提升网关与高并发服务吞吐量

写在最后

SmartMall 是我对微服务架构的一次完整实践，从服务拆分、远程调用、消息驱动到分布式治理，力求覆盖一个生产级电商系统所需的核心技术点。项目的初衷不是做一个"能用就行"的 demo，而是在每个技术决策上追问"为什么"——为什么用最终一致性而不是强一致性？为什么用 Redis 分布式信号量而不是数据库行锁？为什么购物车需要离线与在线合并？
